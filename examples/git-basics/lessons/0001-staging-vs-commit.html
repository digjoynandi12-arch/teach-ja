ステージングとコミットの違い

変更は「3つの場所」を順に進みます。git add と git commit は、その場所を1つずつ進めるコマンドです。

今日できるようになること
git status の表示を見て、変更が今どこにあるかを言える。そして、手元の変更のうち選んだ分だけをコミットできる。

プルリクエスト（pull request）でレビューする人が読むのは、あなたのコミットです。「何をコミットに入れるか」を自分で選べることが、来月のチーム開発の土台になります。

1. 変更が通る3つの場所

Gitで管理しているフォルダーには、ファイルの内容を置く場所が3つあります[1]。

作業ディレクトリ（working directory）
今、エディターで編集しているファイルそのもの
git add
ステージングエリア（staging area）
次のコミットに入れる内容の置き場
git commit
リポジトリ（repository）
コミットが積み重なった履歴
  • ステージする（git add）: 作業ディレクトリの今の内容を、ステージングエリアに写します。「次のコミットにはこれを入れる」と選ぶ操作です。履歴にはまだ何も記録されません。
  • コミット（commit）する（git commit）: ステージングエリアの内容を、メッセージ付きで履歴に記録します。

ここが要点です。コミットが記録するのは、作業ディレクトリではなくステージングエリアの内容です。Pro Gitにも「コミットが記録するのは、ステージングエリアのスナップショットである」と書かれています[2]。

買い物にたとえると、作業ディレクトリは棚の前で手に取った商品、ステージングエリアは買い物かご、コミットはレジでの会計です。かごに入れていない商品は、会計には含まれません。

なぜ、わざわざ2段階なのでしょうか

作業中は、関係のない変更が混ざりがちです。バグを直しながら、ついでに別のファイルの誤字も直した、という場面です。ステージングエリアがあるおかげで、「バグ修正」と「誤字修正」を別々のコミットに分けられます。1つのコミットが1つの目的にまとまっていると、レビューする人は読みやすくなります。

2. 動かして確かめる

下のシミュレーターで、memo.txt という1つのファイルが3つの場所をどう進むかを確かめてください。朱色の行は「右隣の場所にまだ届いていない行」です。ボタンを押す前に、どの欄がどう変わるかを予想してから押すと、よく身につきます。

課題3で、リポジトリは3行ではなく2行になりました。git add したあとに書き足した「パン」は、ステージングエリアに入っていないからです。Gitは「git add コマンドを実行した時点の状態のファイル」をステージします[2]。あとから編集した分を入れたいときは、もう一度 git add します。

3. git status を読む

git status は、変更が今どこにあるかを教えてくれるコマンドです[2]。迷ったら、まずこれを打ちます。見出しは英語ですが、覚えるのは3つだけです。

見出し意味コミットに入るか
Changes to be committedステージ済みの変更。ステージングエリアにあります。入ります
Changes not staged for commit編集したが、まだステージしていない変更。作業ディレクトリだけにあります。入りません
Untracked filesGitがまだ一度も追跡していない新しいファイル。入りません

同じファイルが上の2つの欄に同時に出ることがあります。シミュレーターの課題2の状態です。故障ではなく、「ステージした分」と「そのあと編集した分」が両方ある、という意味です。

4. 自分のターミナルで試す

練習用のフォルダーを作って、本物のGitで同じことを確かめます。仕事のリポジトリには触りません。各手順で、git status の表示を予想してから実行してください。

  1. 練習用のリポジトリを作ります。 
    mkdir git-practice
cd git-practice
git init
  2. ファイルを作って、状態を見ます。 
    echo "牛乳" > memo.txt
git status

    Untracked files の欄に memo.txt が出ます。

  3. ステージして、もう一度見ます。 
    git add memo.txt
git status

    Changes to be committed の欄に移ります。

  4. コミットします。 
    git commit -m "買い物メモを追加"
git status

    nothing to commit と出ます。3つの場所が同じ内容になった、という意味です。

  5. ここからが本番です。ステージしたあとに、もう一度編集します。 
    echo "卵" >> memo.txt
git add memo.txt
echo "パン" >> memo.txt
git status

    memo.txt が Changes to be committed と Changes not staged for commit の両方に出ます。

  6. 2種類の差分を見比べます。実行する前に、どちらに「卵」が出て、どちらに「パン」が出るかを予想してください。 
    git diff --staged
git diff
    答えを見る

    git diff --staged は、ステージングエリアと最後のコミットを比べるので「卵」が出ます。git diff は、作業ディレクトリとステージングエリアを比べるので「パン」が出ます[2]。

  7. コミットして、状態を見ます。 
    git commit -m "卵を追加"
git status

    コミットしたのに、memo.txt が Changes not staged for commit に残ります。「パン」はステージしていなかったからです。

表示が違ったときは。この手順の表示は、Pro Gitの記載[2]をもとに書き、2026年11月15日に実際のターミナルで確認しました。Gitのバージョンによって文言が少し違うことがあります。手順4で名前とメールアドレスの設定を求められたら、Pro Gitの「最初のGitの構成」を見るか、表示をそのままエージェントに貼ってください。

5. 思い出して答える

上を見返さずに答えてください。思い出そうとすること自体が、記憶を強くします。
