履歴を読む・コミットを分ける

git log は、積み重なったコミットを読むコマンドです。読む側に立つと、どんなコミットを作ればよいかが見えてきます。

今日できるようになること
git log で履歴を読み、どのコミットが何を変えたかを言える。そして、混ざった変更を「1つの目的に1つのコミット」に分け、内容が伝わるメッセージを付けられる。

プルリクエスト（pull request）を出すと、レビューする人はあなたのコミットを1つずつ読みます。今日は先に「読む側」を体験し、そのあとで「読まれる側」としてコミットを作ります。

1. まず、前回を思い出す

レッスン1 を見返さずに答えてください。時間をあけて思い出すことが、記憶を長持ちさせます。

2. 履歴は、コミットの積み重ね

git commit をするたびに、リポジトリ（repository）にコミットが1つ積まれます。この積み重ねが履歴です。git log は、それを新しい順に表示します。つまり、直近のコミットがいちばん上に出ます[1]。

$ git log
commit 3f2a9c1e5b7d…（40文字） (HEAD -> main)
Author: 山田 花子 <hanako@example.com>
Date:   Sun Nov 15 10:12:45 2026 +0900

    卵を追加

commit b81d04e9a6c2…（40文字）
Author: 山田 花子 <hanako@example.com>
Date:   Sun Nov 15 10:05:10 2026 +0900

    買い物メモを追加

これは形を示すための例で、値は架空です。1つのコミットにつき、次の4つが表示されます[1]。

行意味
commit 3f2a9c1…コミットハッシュ（commit hash）。コミット1つずつに付く、重複しない名前です。先頭の7文字ほどでも通じます。
Author:コミットした人の名前とメールアドレス。
Date:コミットした日時。
字下げされた行コミットメッセージ（commit message）。git commit -m "…" で付けた説明です。

(HEAD -> main) のような表示は、ブランチのレッスンで扱います。今は読み飛ばしてかまいません。Pro Gitでは、コミットハッシュを「SHA-1 チェックサム」と呼んでいます。同じものです。

見たいものに合わせて、表示を変える

コマンド見えるもの使う場面
git log --oneline1コミットを1行で。短いハッシュとメッセージの1行目[3]全体の流れをつかむ
git log --stat各コミットで変更されたファイルの一覧と、追加・削除された行数[1]どのコミットがどのファイルに触ったかを見る
git log -p各コミットの差分そのもの[1]変更の中身を読む
git log -2直近の2件だけ（数字は自由）[1]最近の分だけ見る。上の3つと組み合わせられます
git show最新のコミット1つの、メッセージと差分[4]今コミットしたものを確かめる

画面が止まったら q を押します。Gitは長い出力を1ページずつ表示します[1]。左下に : が出て入力できなくなったように見えたら、スペースキーで次のページ、q で終了です。壊れたわけではありません。

3. 読みやすい履歴は、分け方とメッセージで決まる

次の2つの履歴を見比べてください。どちらも、同じ変更を記録したものです。

e09a6b3 いろいろ修正
7c5e2fa READMEの誤字を修正
b81d04e ボタンの色を青に変更
3f2a9c1 空のパスワードでログインできるバグを修正

下の履歴なら、レビューする人はバグ修正だけを落ち着いて読めます。あとで「このバグはいつ直したのか」を探すときも、すぐに見つかります。Pro Gitは、コミットの指針として次の2つを挙げています[2]。

  • 1つの目的に、1つのコミット。「コミットの単位が論理的に独立した変更となるように」し、修正した問題ごとにコミットを分けます。分けるのはファイルごとではなく、目的ごとです。1つのバグ修正が2つのファイルにまたがるなら、その2つは同じコミットに入れます。
  • メッセージの1行目は、変更の短い概要。Pro Gitは、1行目に概要を書き、詳しい説明が必要なら空行を1つはさんで続ける形を勧めています。「修正」「更新」だけでは、読む人は差分を開くまで何もわかりません。

目的ごとに分けるための道具が、レッスン1のステージングエリア（staging area）です。「次のコミットの下書き」に、今回の目的に合う変更だけを入れます。

4. 動かして確かめる

作業ディレクトリ（working directory）に、4つのファイルの変更がたまっています。これを、レビューする人が読みやすいコミットに分けてください。入れたい変更をステージし、メッセージを選んで git commit を押します。コミットするたびに、履歴に講評が付きます。

すべて「良い」になったら、もう一度やり直して、わざと全部を1つのコミットにまとめてみてください。講評がどう変わるかを見ると、分ける理由がはっきりします。

5. 自分のターミナルで試す

レッスン1で作った git-practice フォルダーの続きです。前回の最後、「パン」の行はステージしないまま残っていました。各手順で、表示を予想してから実行してください。

  1. 練習用のフォルダーに入り、これまでの履歴を読みます。 
    cd git-practice
git log

    コミットが2つ出ます。上が「卵を追加」、下が「買い物メモを追加」です。新しいほうが上です。

  2. 買い物メモとは関係のない、別の目的の変更を足します。git status の表示を予想してから実行してください。 
    echo "月曜: 掃除" > todo.txt
git status
    答えを見る

    memo.txt が Changes not staged for commit に、todo.txt が Untracked files に出ます。目的の違う2つの変更が、作業ディレクトリに混ざっている状態です。

  3. 目的ごとに、2つのコミットに分けます。 
    git add memo.txt
git commit -m "パンを追加"
git add todo.txt
git commit -m "やることリストを追加"
  4. 履歴を1行ずつで見ます。何行出て、いちばん上はどれでしょうか。 
    git log --oneline

    4行出ます。いちばん上が「やることリストを追加」です。行の先頭にあるのが、短いコミットハッシュです。

  5. 直近の2件について、どのファイルが変わったかを見ます。それぞれのコミットにどのファイル名が出るかを予想してください。 
    git log --stat -2
    答えを見る

    「やることリストを追加」には todo.txt だけが、「パンを追加」には memo.txt だけが出ます。目的ごとに分けたので、1つのコミットが1つのことだけを語っています。

  6. 最新のコミットの中身を読みます。レビューする人が見るのは、この表示に近いものです。 
    git show

    メッセージ「やることリストを追加」のあとに、+月曜: 掃除 という行が出ます。先頭の + は、追加された行という意味です。

表示が違ったときは。この手順は、Pro Git[1] とGitの公式リファレンス[3][4] をもとに書きました。今回は、教える側の環境で実際のGitを動かして確かめることができていません。手元の表示が上の説明と違ったら、表示をそのままエージェントに貼ってください。前回のあとに git-practice を触っていて、コミットの数が違う場合も同じです。

7. 次に読むもの

今日の内容の一次情報源は、Pro Git 第2版の次の節です。git log のオプションが、実際の出力と一緒に紹介されています。

  • 日本語Pro Git 2.3 コミット履歴の閲覧（英語原文）

日本語訳は少し古く、例の日付は2008年で、ブランチ名は master です。また、--oneline ではなく --pretty=oneline という書き方で紹介されています。--oneline は、それにハッシュの短縮を加えた省略形です[3]。節の後半（--pretty=format や --graph）は、今は読み飛ばしてかまいません。

早見表は リファレンス: 履歴を読む・コミットを分ける にまとめました。印刷もできます。

コミットメッセージの書き方は、チームごとに決まりがあることが多いです（日本語か英語か、先頭に種類を書くか、など）。社内の #git-help チャンネルで「コミットメッセージに決まった書き方はありますか」と聞いてみてください。チームのリポジトリで git log --oneline を打って、先輩たちのメッセージを読むのも良い方法です。
